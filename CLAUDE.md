# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Snakemake pipeline that trains ChromBPNet models on ATAC/DNase BAMs, then runs prediction, contribution scores, TF-MoDISco motif discovery (+ MEME export), Fi-NeMo motif hit calling and TOBIAS BINDetect footprinting on the contribution tracks. Runs on a SLURM cluster (IRB Barcelona); GPU rules use RTX 3090s in `irb_gpu_3090` (max 2 GPUs per user at a time) and, for short jobs, the preemptible `spot_gpu` (see GPU partitions below).

## Running

All commands run from the repo root (paths like `config/...`, `data/...` are relative to it).

- Full run (SLURM head job; extra args pass through to snakemake): `sbatch slurm_run_pipeline.slurm`
  - It activates the `snakemake` conda env, unlocks and cleans shadow dirs, then runs `snakemake --profile config/snakemake_profile/slurm "$@"`.
- Dry run / DAG check (safe in the login shell): `snakemake -n --profile config/snakemake_profile/slurm` (add the same `--configfile` you would pass to the head job).
- Single target: `snakemake -n --profile config/snakemake_profile/slurm <output_path>`, e.g. `pred_bw/<sample>_fold_0_chrombpnet_nobias.bw` (relative to `output_dir`). Swap `-n` for a real run only through the sbatch head job. Put targets before `--config key=value` (otherwise they are parsed as more config values).
- Small end-to-end test (2 downsampled samples, 2 folds, 2 epochs, generated splits): `sbatch slurm_run_pipeline.slurm --configfile config/test/config.yaml`. Output dir `/scratch/qscd/dfernandezp/chrombpnetTest`; its downsampled BAMs live in `input_bams/` there (see `config/test/samples.tsv`).
- Tppp3 runs (real data, 5 folds): `config/tppp3/bpnetlite.yaml` (full run, `/scratch/qscd/dfernandezp/Tppp3-bpnet-lite`) and `config/tppp3/chrombpnet.yaml` (`/scratch/qscd/dfernandezp/Tppp3-chrombpnet`: a copy of the first run's models and preprocessing, rerun from `contribs_chunk` with `--forcerun contribs_chunk` and the chrombpnet backend, to compare the backends on the same models).
- GPU sanity check: request target `logs/gpu_test/tensorflow_gpu_check_successful.flag` (rule `gpu_test_rule`, script `workflow/scripts/test_gpu_chrombpnet.py`). `..._successful_<n>.flag` runs extra copies (e.g. to check the partition routing in `logs/gpu_routing.log`).

There are no unit tests; validate changes with `snakemake -n -p` (and `--lint`). The python scripts in `workflow/scripts/` (fold averaging, `parallel_contribs.py`, `merge_contribs.py`, `modisco_to_meme.py`...) are standalone CLIs and can be tested on tiny files inside the chrombpnet image (`singularity exec --bind /home,/scratch/qscd <image> python ...`; DeepSHAP also runs on CPU for a few regions). `bpnetlite_contribs.py` needs the `workflow/envs/bpnetlite.yaml` env instead (a copy is at `/scratch/qscd/dfernandezp/bpnetlite_dev/env`, with the validation scripts in `validation/` there). Run anything heavier than that through `sbatch`/`srun`.

The profile (`config/snakemake_profile/slurm/config.yaml`) uses the SLURM executor, `use-singularity` with `--bind /home,/scratch/qscd --nv` (GPU passthrough), conda for TF-MoDISco, TOBIAS, Fi-NeMo and the bpnet-lite contribs, `keep-going`, `slurm-requeue` (see GPU partitions) and default account `qscd` / partition `irb_cpu_iclk`.

## Configuration

- `config/config.yaml`: genome build, output dir (`/scratch/qscd/dfernandezp/chrombpnet`), folds to run (`folds: ["0"]` by default), MACS3/ChromBPNet/MoDISco params, contribution scores (`contribs`: backend, chunking, batch size/precision), QC MoDISco (`qc_modisco`), Fi-NeMo (`finemo`), container images. The chrombpnet image is pinned by digest because rules call its internal modules (`python -m chrombpnet....`); check them again before changing it. Note the keys are spelled `chromnpnet_bias` / `chromnpnet_model` (typo is load-bearing; rules reference these exact names).
- `config/samples.tsv`: `SampleName`, `BamPath` (multiple BAMs separated by `;`, merged per sample), `UseForBiasModel` (`True` samples' BAMs are all pooled into a single bias model).
- `config/resources.yaml`: per-rule `mem_mb`/`runtime` (minutes)/`cpu`/`retries`, plus `gres`/`slurm_partition` for GPU rules, and the `gpu_routing` block. Every rule reads its resources via `RESOURCES["<rule_name>"]`, so adding a rule means adding an entry here. The SLURM plugin takes CPUs from `threads:` (the `cpu` key only feeds it). A run's `--configfile` can change entries with `resource_overrides`, merged rule by rule (e.g. `config/tppp3/bpnetlite.yaml` lets training overflow to `spot_gpu`).
- Fold splits: `splits_dir` (default `config/chr_splits`, pre-made mm10 `fold_N.json`) is used as is. If `splits_dir: ""`, rules `get_canonical_chrom_sizes` + `make_chr_splits` generate them with `chrombpnet prep splits` from `chr_splits.folds` (test/valid chroms per fold) into `<output_dir>/chr_splits/`. Rules refer to the fold file through the `FOLD_JSON` global.
- `config/Blacklist/`: vendored ENCODE Blacklist repo; the pipeline only uses `lists/<build>-blacklist.v2.bed.gz` unless `custom_blacklist` is set.

## Architecture

`output_dir` holds everything that is not pipeline code/config: the Snakefile sets `workdir: OUTPUT_DIR`, so `.snakemake/` (singularity images, conda envs, metadata, slurm logs, shadow dirs), downloaded reference data (`data/`), the singularity pull cache (`.singularity_cache/`), the conda package cache (`.conda_pkgs/`), tmp files and results all go there. Point it to `/scratch` for real runs (home has a small quota). Consequences: relative paths in the config (sample sheet, its BAMs, resources, blacklist, `splits_dir`, `output_dir`) are relative to the repo root and must be wrapped in `repo_path()` in the Snakefile *before* the `workdir:` line (SLURM rule jobs re-parse the Snakefile from inside `output_dir`, so the current directory can't be used); rule inputs/outputs are written as plain relative paths (no `OUTPUT_DIR` prefix, so no f-strings unless a value like `TOP_N_PEAKS` is interpolated) and resolve inside `output_dir`. Singularity binds `/home` and `/scratch/qscd` (never the whole `/scratch`: the chrombpnet image has its code and data under `/scratch/chrombpnet`, which would be hidden), so `output_dir` must be under one of them.

`workflow/Snakefile` loads config, parses the sample sheet into `SAMPLES` and `ALL_BIAS_BAMS`, defines shared globals (`OUTPUT_DIR`, `GENOME_FASTA`, `TOP_N_PEAKS`, `FOLDS`, ...) used by all rule files, sets `TMPDIR`/`SINGULARITY_TMPDIR` to `<output_dir>/<host_tmp_dir>`, then includes rules in order (later files reference `rules.<name>.output` from earlier ones):

0. `common.smk`: GPU partition routing (`gpu_partition()`) and `thread_env()` (caps the thread pools of TensorFlow/OpenBLAS/numba to the job's CPUs; GPU/MoDISco rules `export` it).
1. `prepare_data.smk`: downloads genome FASTA, chrom sizes, JASPAR motifs into `<output_dir>/data/`; unzips the blacklist; merges/sorts/indexes per-sample BAMs (`scripts/merge_sort_index_bams.sh`: coordinate-sorted inputs are symlinked or merged without re-sorting).
2. `generate_bias_model.smk`: pools all bias BAMs → MACS3 → blacklist filter (blacklist slopped by 1057 bp = half ChromBPNet input) → top-N peaks (`scripts/filter_top_peaks.py`: canonical chromosomes only (`chr_splits.canonical_chroms_regex`), exactly N by column 7, original order) → `chrombpnet prep nonpeaks` → `chrombpnet bias train` per fold. The bias QC that `chrombpnet bias pipeline` would run in the same GPU job is split so model training doesn't wait for it: `bias_qc_gpu` (predictions + DeepSHAP on 30K peaks), `bias_qc_modisco` (CPU, per `{head}` profile/counts) and `bias_report` (converts the MoDISco reports to PDF, then `make_html_bias -icmd pipeline` → `evaluation/overall_report.html`).
3. `preprocessing.smk`: the same peak/nonpeak steps per sample.
4. `training.smk`: `chrombpnet train` per sample × fold, using the fold's shared bias model. Produces `*_chrombpnet_nobias.h5` (and `*_train_report.html`).
5. `qc.smk`: the QC of `chrombpnet pipeline`, rebuilt from parts: `chrombpnet_qc_gpu` (test-set metrics with `python -m chrombpnet.training.predict`, marginal footprints of the bias motifs in `workflow/motifs/` → max bias response), `chrombpnet_qc_modisco` (CPU MoDISco on the first `qc_modisco.n_regions` rows of the fold's all-peaks contribs) and `chrombpnet_report` (MoDISco report to PDF, then `make_html -icmd pipeline` → `evaluation/<sample>_overall_report.html`). No GPU DeepSHAP on a separate 30K subsample.
6. `prediction.smk`: per sample × fold `pred_bw` and `chrombpnet footprints` (motifs from `footprints.motifs_to_pwm` inserted in the fold's test-chromosome nonpeaks); contribution scores via `split_contribs_regions` (shuffles the sample's peaks with a fixed seed and splits them into `contribs.n_chunks` beds, identical for all folds) → `contribs_chunk` (GPU; `contribs.backend`: `bpnetlite` runs `scripts/bpnetlite_contribs.py` in the conda env `workflow/envs/bpnetlite.yaml`, `chrombpnet` runs `scripts/parallel_contribs.py` with `contribs.procs_per_gpu` chrombpnet interpret processes in the chrombpnet image) → `merge_contribs` (CPU; `scripts/merge_contribs.py` concatenates in order and writes the bigwigs with chrombpnet's `bigwig_helper`). Final files are those of `chrombpnet contribs_bw`, **but their rows are in shuffled order** (TF-MoDISco's `-n` cap keeps seqlets in region order). Per sample `modisco motifs` + `modisco report` on the fold-averaged profile scores, and `modisco_meme` (`scripts/modisco_to_meme.py`, trimmed PFMs).
7. `fold_average.smk`: per sample, averages folds (`{sample}_mean*` outputs) with `scripts/average_bigwigs.py` (prediction and contribution bigwigs) and `scripts/average_contribs_h5.py` (contribution h5; requires identical `interpreted_regions.bed` across folds). With one fold the mean equals that fold.
8. `tobias.smk`: merges all samples' (fold-averaged) interpreted regions into consensus peaks, then runs TOBIAS BINDetect twice (profile and counts contribution bigwigs as "footprint" signals, one condition per sample). Uses the conda env `workflow/envs/tobias.yaml` (bioconda `tobias` package; installing it with pip no longer builds), not a container, and forces `TMPDIR=/tmp`.
9. `finemo.smk`: Fi-NeMo on each sample's fold-averaged profile contribs (same h5 as MoDISco; the mean bed gives the peak coordinates in the same row order) and its MoDISco h5: `finemo/<sample>/hits/` (hits.tsv, hits_unique.tsv, hits.bed) and `finemo/<sample>/report/` (motif_occurrences.tsv = hits per motif per peak). Conda env `workflow/envs/finemo.yaml` (PyPI torch wheel with bundled CUDA); `finemo_call_hits` needs a GPU.

`wildcard_constraints` in the Snakefile restrict `sample` to the sample names, `fold` to digits, `chunk` to 3 digits and `head` to profile/counts, which keeps `{sample}_fold_{fold}*`, `{sample}_mean*` and chunk patterns unambiguous.

GPU partitions: `irb_gpu_3090` (irbgcn01) runs at most 2 GPUs per user (QOS `gpulimits`); `spot_gpu` has more 3090 nodes and no limit, but jobs can be preempted. A single job can't target both (different QOS, `EnforcePartLimits=ALL`), so `gpu_partition()` picks one per job at submission time from `slurm_partition` in resources.yaml: `main` (training: always `irb_gpu_3090`), `auto` (short jobs: `irb_gpu_3090` while the user has < `gpu_lane_limit` jobs there per `squeue`, else `spot_gpu`; retries after a failure go to `irb_gpu_3090`) or a fixed name. Decisions go to `logs/gpu_routing.log`; the callable returns the main partition in dry runs and inside cluster jobs. The cluster has `JobRequeue=0`, so the profile sets `slurm-requeue: true`: without it a preempted job is cancelled while the slurm plugin keeps waiting for it. Rules that can land on spot must therefore be restartable from scratch. TensorFlow rules always request `gpu:rtx3090` (TF 2.8 in the chrombpnet image JIT-compiles and hits cuDNN errors on the H200s; 4090s are also unsupported); PyTorch rules (bpnet-lite contribs, Fi-NeMo) request any GPU (`gpu:1`), so on `spot_gpu` they can also run on the H200/4090 nodes.

Contribution score backends: `bpnetlite_contribs.py` computes chrombpnet's DeepSHAP with bpnet-lite/tangermeme's API (the user wants their API used as is, so library updates flow through): `BPNet.from_chrombpnet` (its forward matches chrombpnet's crops only for the 8-layer accessibility model, the only model this step sees; the bias QC still uses chrombpnet's DeepSHAP), `CountWrapper`, `bpnetlite.attribute.deep_lift_shap`, `tangermeme.io.extract_loci` (summit-centered windows), and peaks containing N are skipped as `bpnet attribute` does. The only own code is `ProfileTarget`, because bpnet-lite's `ProfileWrapper` is numerically unstable: tangermeme's rescale rule divides each position's change of logits·softmax(logits) by the change of its own logit, which explodes where a logit barely changes. Its scores still sum to the change in prediction (no convergence warning) but agree with chrombpnet's at r ~0.68 and between independent seeds at ~0.46 (checked with bpnet-lite's own `bpnet attribute`; issue draft and scripts in `/scratch/qscd/dfernandezp/bpnetlite_dev/validation/upstream_check/`). `ProfileTarget` reproduces how shap's TF DeepExplainer handles chrombpnet's `sum(logits * softmax(stop_gradient(logits)))`: that shap fork has no StopGradient handler, so the logits get the multiplier (w_input + w_reference)/2, done by averaging the softmax weights of each input-reference pair in tangermeme's concatenated batch. If bpnet-lite fixes `ProfileWrapper`, switch to it and revalidate. Validated on 2000 peaks of the test model: predictions equal TF (max diff 7e-4); per-peak r with chrombpnet equals chrombpnet's run-to-run r (0.85 profile / 0.88 counts); float16 vs float32 r = 1.0000 at 1.6x the speed (its counts convergence deltas reach ~0.01 from rounding, hence a 2e-2 warning threshold in float16). Precision is set by casting the model (`contribs.dtype`), as `bpnet attribute` does. tangermeme seeds reference k with `random_state + k` for every region, so runs compared for reproducibility need seeds far apart (seeds 0 and 1 share 19 of 20 references).

Conventions to preserve:
- ChromBPNet refuses to write into an existing output dir, but Snakemake pre-creates output parents. Training rules therefore write to a `tmp_*` dir, `mv` it to the final location, and touch a `complete.flag`. They rename chrombpnet's train-only `overall_report` to `train_report`; the full `evaluation/*overall_report.html` QC reports (used to tune `bias_thresh_factor`) are written by the report rules into the same model dirs, with the file names chrombpnet's report generators expect (QC rules write there too, so keep those names). `chrombpnet qc` / `bias qc` can't be used standalone (they require a new output dir but read `auxiliary/filtered.*` from it).
- Contribution score chunk files are `temp()` unless `contribs.keep_chunks`; changing `contribs.n_chunks` or `shuffle_seed` recomputes all contribution scores.
- `chrombpnet prep nonpeaks` rules use `shadow: "minimal"` (hence `--cleanup-shadow` in the head script).
- Most rules run inside `chrombpnet_container` (which also provides samtools/bedtools); MACS3 and bedtools-only steps use their own biocontainers.
- TF-MoDISco (`bias_qc_modisco`, `chrombpnet_qc_modisco`, `modisco_tf`) runs modisco-lite 2.4.0 in the conda env `workflow/envs/modisco.yaml`, not the image's 2.0.7, which crashes in `_extract_gkmers` ("cannot assign slice from input of different size") when a seqlet has fewer gapped k-mers than `max_entries` (it happened on a Tppp3 bias QC; fixed upstream in 2.3.2). 2.4.0 exposes settings that 2.0.7 hardcoded, with other defaults, so `MODISCO_MOTIFS_ARGS` in `common.smk` (`-z 20 -t 20 -f 5 -g 5 -j 0`) restores 2.0.7's (the `TFMoDISco` signatures otherwise match). The MEME db (`modisco_tf.meme_db`, a path inside the ChromBPNet image) is copied to `data/modisco_motifs.meme.txt` by `get_modisco_meme_db`; the report rules make the MoDISco PDFs because chrombpnet's `convert_html_to_pdf` needs the image.
- `/scratch` purges files with mtimes older than ~60 days, and conda keeps the packages' original mtimes, so an `onstart:` handler in the Snakefile touches the files of `.snakemake/conda` and `.conda_pkgs` older than 30 days on every run. If an env breaks anyway (e.g. `ModuleNotFoundError` inside it after a long pause), delete those two dirs in `output_dir`.
- The Snakefile uses nested same-quote f-strings, which requires Python ≥ 3.12 in the snakemake env.
- The Snakefile sets `SINGULARITY_CACHEDIR` (the cluster runs SingularityCE) but must not set `APPTAINER_CACHEDIR`: snakemake uses that variable as the directory of the pulled images (`--apptainer-prefix`), which the cluster jobs inherit while the main process has already chosen `.snakemake/singularity`, so the jobs kept their own copies in `.singularity_cache/` and, in a fresh or copied output dir, every container job pulled the image itself.
